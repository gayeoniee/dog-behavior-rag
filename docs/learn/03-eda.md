## 1. 왜 통계부터 보나

### 왜 필요한가

이 프로젝트의 청크 크기는 **1,200자**다. 왜 1,200자인가?

**근거가 없다.** 그럴듯해서 골랐다. `app/core/config.py`에 남은 주석이 솔직하다 —
"top_k=5 × 1200자 ≈ 6000자. 다음 라운드에 어떤 LLM을 붙여도 프롬프트에 들어간다."
즉 **프롬프트에 들어가는 크기**를 기준으로 정했지, 내 문서가 어떻게 생겼는지는
보지 않았다.

멘토의 조언이 정확히 이 지점이다:

> eda같은 간단 데이터 분석을 하는 스크립트를 짜달라고 해서 **통계 보고 청킹 방식을
> 정하는 게** 좋습니다. 데이터 샘플 직접 검사해서 청킹 방식을 정해야 합니다.

이 프로젝트는 이걸 안 해서 이미 한 번 크게 헤맸다. 코퍼스를 11건 → 282건으로
**25배** 늘렸는데 체감 품질이 그대로였다. 늘어난 266건이 전부 논문이라, 보호자가
매일 묻는 배변·뛰어오르기·줄당김에는 전용 문서가 **하나도** 없었기 때문이다.
통계를 한 번만 봤으면 늘리기 전에 알았을 일이다.

### 직접 확인

```bash
uv run python -m scripts.eda.corpus_stats            # 기본 리포트
uv run python -m scripts.eda.corpus_stats --tokens   # 실제 토큰 수까지 (모델 필요)
uv run python -m scripts.eda.corpus_stats --size 800 # 다른 청크 크기면 어떻게 되나
uv run python -m scripts.eda.corpus_stats --sample 2 # 본문 샘플을 눈으로
```

**DB도 torch도 필요 없다** (`--tokens` 제외). `corpus.jsonl`만 읽으므로 수집만
끝난 상태에서도 돌아간다.

## 2. 리포트 읽는 법

### ① 문서 개요 — 무엇이 얼마나 있나

```
  문서 294건 · 총 9,799,961자
  종류    논문 263 · 가이드 31

  문서 길이  최소 1,236 · p25 23,850 · 중앙 32,458 · p75 42,215 · 최대 82,083자

       < 2,000  ██                                            7 ( 2.4%)
      < 10,000  █████                                        18 ( 6.1%)
      < 20,000  ███████                                      27 ( 9.2%)
      < 40,000  ████████████████████████████████████████    158 (53.7%)
      < 60,000  █████████████████                            68 (23.1%)
     >= 60,000  ████                                         16 ( 5.4%)
```

**왜 평균이 아니라 백분위인가:** 평균은 긴 문서 하나에 끌려간다. 중앙값(32,458자)은
"딱 가운데 문서"의 크기라 훨씬 정직하다.

**읽어야 할 것:** 절반 이상(53.7%)이 2~4만 자다. 이걸 통째로 프롬프트에 넣는 건
불가능하다 → **청킹은 선택이 아니라 필수다.**

### ② 문서 구조 — 무엇을 기준으로 자를 수 있나

청크 크기는 **문단 길이와 비교해서** 정해야 한다.

```
  ── 논문 263건 ──
  문단 길이      최소 2 · p25 60 · 중앙 506 · p75 939 · p95 1,802자
  줄 길이        최소 1 · p25 45 · 중앙 430 · p75 880 · p95 1,740자
  제목형 줄 비율  16.6%

  ── 가이드 31건 ──
  문단 길이      최소 1 · p25 21 · 중앙 87 · p75 281 · p95 1,020자
  줄 길이        최소 1 · p25 28 · 중앙 48 · p75 67 · p95 377자
  제목형 줄 비율  38.6%
```

**논문과 가이드는 아예 다른 문서다:**

| | 논문 | 가이드 | 몇 배 |
|---|---|---|---|
| 문단 중앙값 | 506자 | 87자 | **5.8배** |
| 줄 중앙값 | 430자 | 48자 | **9배** |
| 제목형 줄 | 16.6% | 38.6% | |

이유는 **출처가 달라서**다. 논문은 PMC API의 XML 본문이라 문단이 통짜로 오고,
가이드는 HTML 페이지에서 뽑아서 **줄 하나가 목록 항목 하나**다
("1. 문을 열어둔 채 간식을 넣어줍니다").

### ③ 청킹 시뮬레이션

```
  청크 11,354개 · 문서당 중앙 38개
  청크 길이   최소 154 · p25 897 · 중앙 1,061 · p75 1,140 · 최대 1,200자
  전처리 제거 15,909자 (머리글·페이지번호·하이픈 줄바꿈)

  문장부호로 끝난 청크    5,054 / 11,354 (44.5%)
  ⚠ 문장 중간에서 끊긴 청크 4,854 / 11,354 (42.8%)
```

> ✅ **시뮬레이션 결과 11,354개는 DB에 실제로 들어 있는 청크 수와 정확히 같다.**
> 스크립트가 진짜 청킹 코드(`app/services/chunking.py`)를 그대로 부르기 때문이다.
> 별도로 구현했으면 여기서부터 거짓말이 시작된다.

### ④ 임베딩 입력 예산

```
  표본 1,361청크 · 계산 방식: 실제 토크나이저 (BAAI/bge-m3)
  토큰 수   최소 32 · p25 216 · 중앙 248 · p75 270 · p95 311 · 최대 620토큰

  모델 상한 8,192토큰   대비 p95 사용률  3.8%
  설정 상한 1,024토큰   대비 p95 사용률 30.4%   ← 실제로 적용되는 쪽

  ✓ 잘리는 청크 없음 (최대 620토큰 < 1,024)
```

**토큰이 뭔가:** 모델은 글자를 **"토큰"** 단위로 묶어 읽는다. 영어는 대략 4자 ≈ 1토큰
(우리 청크는 1,061자 ≈ 248토큰이니 4.3자/토큰).

**넘치면 어떻게 되나:** 임베딩 모델에는 **최대 입력 길이**가 있고, 넘으면 뒤가 **조용히
잘린다.** 에러도 경고도 없이 그냥 없는 셈이 된다.

> ⚠️ **상한이 두 개다. 헷갈리기 쉬운 지점이다.**
> bge-m3 자체는 8,192토큰까지 받지만, 이 프로젝트는
> `Settings.embedding_max_seq_length = 1024`로 **잘라 쓴다** (CPU 메모리
> 스파이크를 막으려고). 그래서 비교해야 할 값은 8,192가 아니라 **1,024**다.
>
> 다행히 가장 긴 청크가 620토큰이라 지금은 잘리는 게 없다. 하지만 청크 크기를
> 2,000자로 올리는 실험을 하면 이 상한을 먼저 확인해야 한다. **아니면 늘린
> 만큼이 조용히 버려진다.**

## 3. 이번 EDA로 나온 발견 세 가지

### 발견 1 — 성격이 다른 두 문서에 같은 청킹 규칙을 쓰고 있다

문단이 5.8배 차이 나는데 둘 다 1,200자로 자른다.

- **논문**(문단 506자): 청크 하나에 문단 2개쯤 들어간다. 적당하다.
- **가이드**(문단 87자): 청크 하나에 **목록 항목이 십수 개** 들어간다.
  "켄넬 훈련 5단계"와 "짖음 대처법 3가지"가 한 청크에 섞일 수 있다.

가이드는 청크의 3.7%밖에 안 되지만 **보호자가 실제로 원하는 답이 여기 있다.**
04장에서 문서 종류별로 다른 크기를 쓰는 게 나은지 실험할 항목이다.

### 발견 2 — 입력 예산의 30%만 쓰고 있다 (그리고 상한이 두 개였다)

p95가 311토큰인데 **실효 상한은 `embedding_max_seq_length` 설정값 1,024토큰**이다.
30.4%를 쓰고 있다.

**"그럼 청크를 키우면 되겠네"는 틀린 결론이다.** 청크가 커지면:

- 한 청크에 여러 주제가 섞여 **임베딩이 뭉개진다** (평균 내면 특징이 사라진다)
- 검색이 맞아도 **필요 없는 텍스트가 프롬프트를 먹는다**
- 반대로 너무 작으면 **문맥이 없어** 그 조각만 봐서는 뜻이 안 통한다

이건 **맞교환**이고, 방향은 통계로 못 정한다. 06장의 지표로 재야 한다.

다만 확실해진 게 하나 있다: **청크를 2,000자로 늘리는 실험을 한다면
`EMBEDDING_MAX_SEQ_LENGTH=1024`를 먼저 올려야 한다.** 안 그러면 늘린 만큼이
조용히 잘려서, "청크를 키웠는데 왜 안 좋아지지?"라는 잘못된 결론에 도달한다.
**EDA를 안 했으면 이 함정을 못 봤을 것이다.**

### 발견 3 — 청크의 42.8%가 문장 중간에서 끊긴다

가장 뜻밖의 발견이다. 재귀 분할은 문단 → 줄 → 문장 순으로 자르니 문장은 지킬
거라고 생각했다. 실제 사례를 뽑아보자:

```
청크 0 끝:  ...low-fear and low-stress environment for patients, staff and
청크 1 시작: management into everyday patient care\nusing standardized behavioral...
```

**원인은 구분자 순서다.** `app/services/chunking.py`:

```python
_SEPARATORS = ("\n\n", "\n", ". ", " ")
                       ↑ 줄바꿈이 문장(". ")보다 먼저다
```

PDF에서 뽑은 텍스트의 `\n`은 **인쇄된 줄의 끝**이지 문장의 끝이 아니다.
종이에서 줄이 바뀐 자리일 뿐인데, 코드는 그걸 의미 경계로 취급한다.

이게 알려진 맞교환이라는 것도 확인했다. `clean_for_chunking`의 주석이 이렇게
말한다 — 하드 줄바꿈을 문단으로 합치면 "AAHA PDF에는 도움이 되지만 HTML 문서는
줄 하나가 리스트 항목 하나라 무관한 항목들이 한 문장으로 융합된다."

**판단 자체는 합리적이었다. 다만 대가가 얼마인지 몰랐다.** 이제 안다: 42.8%다.

> 💡 완전히 손실은 아니다. **겹침(overlap) 150자가 이걸 부분적으로 메운다** —
> 위 예에서 잘린 문장이 다음 청크 앞에 다시 들어가 있다. 겹침이 왜 있는지를
> 보여주는 실제 사례다.

## 4. 청크 크기를 바꾸면 어떻게 되나

```bash
uv run python -m scripts.eda.corpus_stats --size 800
```

| 크기 | 청크 수 | 문장부호로 끝남 | ⚠ 문장 중간에서 끊김 |
|---|---|---|---|
| 400자 | 46,751 | 15.1% | **60.1%** |
| 800자 | 17,924 | 30.1% | 50.7% |
| **1,200자 (현재)** | **11,354** | **44.5%** | **42.8%** |
| 2,000자 | 6,684 | 58.3% | 35.5% |

작을수록 문장이 더 많이 깨진다. 문단 중앙값(논문 506자)보다 작아지면 문단을
매번 쪼개야 하니 당연하다.

**그렇다고 2,000자가 정답은 아니다.** 이 표는 "경계가 깨끗한가"만 본다.
**검색을 잘하는가는 전혀 재지 않았다.** 그건 06장의 지표(hit rate·MRR)로만
알 수 있다. 그래서 04장이 아니라 06장 다음에 결론이 난다.

## 5. 지표를 만들면서 배운 것

처음에는 "문장부호로 끝난 비율" 하나만 쟀다. 그런데 그 수치가 **과장돼 있었다.**

가이드 문서는 "1. 간식을 코앞에" 처럼 마침표 없이 끝나는 줄이 정상이다.
그런데 지표는 그걸 전부 "실패"로 셌다. 잘린 게 아니라 원래 그런 문장인데도.

그래서 **애매함이 없는 지표를 하나 더** 만들었다 — 마지막 글자가 소문자나
쉼표면 명백히 문장 중간이다. 목록 항목이나 제목은 여기 안 걸린다.

> **교훈: 넓고 흐린 지표보다 좁고 확실한 지표가 낫다.**
> 이 프로젝트는 이걸 이미 한 번 비싸게 배웠다. 검색 평가셋의 키워드 판정이
> 부분 문자열에 걸려(`tail` ← de**tail**, `aging` ← man**aging**) 주제를 안 다루는
> 근거를 통과로 세고 있었다. **평가가 틀리면 아무도 모른다.**

## 요점 3줄

1. **청킹 크기는 문서 구조와 비교해서 정해야 한다.** 내 코퍼스는 논문 문단 506자 /
   가이드 문단 87자로 **5.8배 차이**인데 같은 규칙을 쓰고 있다.
2. **입력 예산의 30%만 쓰고 있고, 상한이 두 개였다** (모델 8,192 / 설정 1,024).
   비교해야 하는 건 설정값이다. 청크를 키우는 실험을 하려면 이걸 먼저 올려야 한다.
3. **청크의 42.8%가 문장 중간에서 끊긴다.** 원인은 구분자 순서(`\n`이 `". "`보다
   먼저)이고, PDF의 줄바꿈이 의미 경계가 아니기 때문이다.

## 이해 확인 질문

1. 문서 길이를 볼 때 왜 평균이 아니라 중앙값·백분위를 보나?
2. 청크를 2,000자로 키우는 실험을 하려고 한다. 코드를 고치기 전에 반드시
   확인해야 하는 설정값이 하나 있다. 무엇이고 왜인가?
3. 청크 크기를 400자로 줄이면 문장이 60%나 깨진다. 그럼 400자는 나쁜 선택인가?
