## 1. 왜 평가셋을 기계가 만드나

### 왜 필요한가

지금 이 프로젝트의 평가셋은 **21문항**이고 전부 손으로 썼다. 두 가지 문제가 있다.

**(1) 너무 적어서 지표가 흔들린다.** 21문항에서 1문항은 4.8%다. 청킹을 바꿔서
점수가 1문항 움직였다면 그게 개선인지 잡음인지 알 수 없다. 실제로 이 프로젝트는
같은 코드로 두 번 돌렸을 때 점수가 ±1 움직이는 걸 이미 확인했다.

**(2) 내가 아는 것만 묻게 된다.** 질문을 사람이 고르면 **자기가 아는 주제**로
쏠린다. 코퍼스에 뭐가 들어 있는지 다 아는 사람은 없는데도.

### 핵심 아이디어 — 정답 라벨이 공짜다

```
청크 하나를 고른다  →  "이걸로 답할 수 있는 질문"을 LLM에게 만들게 한다
                        ↓
              그 질문의 정답은 정의상 그 청크다
```

사람이 청크 11,354개를 뒤져 "이 질문의 정답은 몇 번"이라고 표시할 필요가 없다.
**질문을 만든 출처가 곧 정답**이기 때문이다.

06장에서 이걸로 hit rate와 MRR을 잰다: 질문을 검색에 넣고 **그 청크가 상위에
올라오는지** 보면 된다.

### 직접 확인

```bash
uv run python -m scripts.eval.generate_qa --n 100 --seed 42
uv run python -m scripts.eval.generate_qa --inspect data/eval_auto_qa.jsonl
```

`--seed`가 있는 이유: 같은 표본을 다시 뽑을 수 있어야 실험이 재현된다.

## 2. 만들면서 부딪힌 것 세 가지

교과서에는 "LLM으로 QA쌍을 생성한다" 한 줄이지만, 실제로 해보면 그 한 줄이
**세 번 무너진다.** 이 절이 이 장의 진짜 내용이다.

### 무너짐 1 — "쓸모없으면 SKIP하라"를 20번 중 0번 지켰다

첫 프롬프트는 질문 생성과 판단을 같이 시켰다:

> 참고문헌 목록, 표 조각, 연구 방법론이면 SKIP을 출력하라

**청크 20개 중 SKIP이 0개였다.** 종양 반응, T세포 증식, 심지어 이런 것까지
질문으로 만들어냈다:

```
✓ 강아지 의사가 돈을 잘 벌었나요?          ← 수의학 역사 문단
✓ 경험 점수가 정답 할당 비율과 어떤 관련이 있나요?   ← 통계 결과
```

**이 프로젝트가 이미 겪은 실패 모드다.** `evidence_select`도 "쓸 근거 고르기 +
개 질문인지 판정"을 한 호출에 묶었다가 후자를 놓쳐 범위 밖 질문 통과율이
1/4이었고, **단답 분류로 떼어내니 4/4**가 됐다.

> **작은 모델은 한 호출에 두 가지를 시키면 하나를 버린다.** 프롬프트에 적혀 있어도
> 안 지킨다. 특히 "무언가를 만들라"는 지시가 섞이면 그쪽이 이긴다 — 만드는 게
> 판단하는 것보다 쉽기 때문이다.

그래서 **판정을 떼어냈다**:

```
① is_owner_useful()   OWNER / RESEARCH   ← 단답 분류
② generate_one()      질문 생성           ← ①을 통과한 것만
```

### 무너짐 2 — 판정에 숙고를 켰더니 전부 RESEARCH가 됐다

이 프로젝트의 규칙은 "숙고가 필요한 곳은 판정뿐"이다. 그대로 `reasoning=True`를
켰더니 **20개 중 18개가 RESEARCH**로 잘렸다. 천둥 공포 같은 명백한 보호자 주제까지.

같은 청크를 두 설정으로 재봤다:

| 설정 | 결과 |
|---|---|
| `reasoning=True`, `max_tokens=8` | `RESEARCH` ← 전부 이렇게 |
| `reasoning=False`, `max_tokens=8` | `OWNER` ← 맞는 판정 |

**사고과정도 completion 토큰을 먹는다.** 예산이 8토큰뿐이니 숙고를 켜면
생각하다 끝나고 답이 기본값으로 눌린다.

> **규칙을 다시 읽어야 했다.** "판정이면 숙고를 켠다"가 아니라
> **"숙고할 여유를 준 경우에만 켠다"**이다. 예산 없이 켜는 건 끄는 것보다 나쁘다.

### 무너짐 3 — 걸러도 공허한 질문이 남았다

`reasoning=False`로 고치니 통과율이 30%가 됐는데, 남은 것 중 절반이 이랬다:

```
✓ 우리 강아지들 모두 건강한 건가요?         ← 아무 문서나 "답"이 된다
✓ 아버지가 개 의사였는데 왜 아들은 다른 일을 했을까요?
```

문제가 두 종류다. **너무 막연해서** 어떤 청크든 정답이 되는 질문, 그리고 청크에
적혀 있긴 하지만 **보호자에게 무의미한** 질문.

그래서 세 번째 단계를 붙였다 — 만든 질문을 되짚어 검증한다:

```
③ answers_question()   YES / NO   "이 발췌로 그 질문에 답이 되나?"
```

여기서도 **한 호출에 한 가지만** 시킨다.

## 3. 최종 구조 — 세 단계 깔때기

```
   청크 표본 (문서당 최대 2개, seed 고정)
        │
        ├─① is_owner_useful    OWNER / RESEARCH      ← 단답 분류
        │
        ├─② generate_one       한국어 질문 생성        ← ①을 통과한 것만
        │      └ 기계 검사: 길이·물음표·"이 문서에 따르면" 류 제거
        │
        └─③ answers_question   YES / NO              ← 단답 분류
                │
          (질문, 정답 청크) 쌍
```

**표본을 뽑을 때 문서당 상한(2개)을 둔다.** 그냥 무작위로 뽑으면 청크가 105개인
논문이 3청크짜리 RSPCA 가이드보다 **35배** 자주 뽑힌다. 그러면 평가셋이 "긴 논문
읽기 시험"이 되어버린다.

### 어휘 누출(leakage)이 구조적으로 막힌다

평가셋 자동 생성의 고전적 함정은 **질문이 청크 표현을 그대로 베끼는 것**이다.
그러면 검색이 부당하게 쉬워져서 점수가 실제보다 높게 나온다.

이 프로젝트는 그게 구조적으로 어렵다. 청크는 **영어**인데 질문은 **한국어**로
만들게 하기 때문이다. 표현이 그대로 넘어올 수 없고, 덤으로 실사용 조건
(한국어 질문 → 영어 코퍼스)과 정확히 같아진다.

## 4. 이 평가셋의 한계 — 06장에서 지표를 읽을 때 반드시 감안할 것

### 한계 1 — "정답은 하나"라는 가정이 틀릴 수 있다

hit rate는 "그 청크가 상위 k에 있나"로 채점한다. 그런데 우리 코퍼스에는
분리불안 청크가 수십 개다. **다른 청크가 1위여도 실제로는 맞는 답일 수 있는데
지표는 틀렸다고 센다.**

> 즉 **점수가 실제보다 낮게 나온다.** 절대값을 신뢰하지 말고
> **같은 평가셋으로 잰 A와 B의 비교**에만 쓰는 게 안전하다.

### 한계 2 — 기계가 만든 질문은 실사용 질문과 다르다

보호자는 "우리 개가 밤에 짖어요"라고 쓴다. 논문 문단을 요약한 질문을 하지 않는다.
**그래서 손으로 쓴 21문항을 버리지 않고 같이 쓴다.** 둘은 쓰임이 다르다:

| | 손으로 쓴 21문항 | 자동 생성 |
|---|---|---|
| 질문의 현실성 | **높다** (실사용 말투) | 낮다 |
| 규모 | 21 | 원하는 만큼 |
| 정답 라벨 | 키워드로 간접 판정 | **청크 단위로 정확** |
| 용도 | 체감 품질·거절 동작 | hit rate·MRR |

### 한계 3 — 생성 품질이 LLM 성능에 묶인다… 고 생각했는데 아니었다

로컬 `gemma-4-e2b`(4.6B)로 100개를 돌린 결과가 **13문항(13%)**이었다.
너무 적어서 "더 큰 모델을 쓰면 나아지겠지" 하고 Gemini로 바꿔봤다.

**0/10이었다. 더 나빠졌다.**

당황해서 판정기가 고장 난 건지 확인했다. 보호자용인 게 확실한 문서
(ASPCA·RSPCA·VCA)의 청크로 같은 판정기를 돌려보니:

| 표본 | OWNER 통과율 |
|---|---|
| 무작위 (코퍼스 그대로 = 논문 96%) | **0/10** |
| 보호자용 기관 문서 | **14/15 (93%)** |

**판정기는 멀쩡했다. 병목은 모델이 아니라 코퍼스였다.**

> **더 강한 모델이 더 엄격했을 뿐이다.** gemma가 13%를 통과시킨 건 관대해서지
> 잘해서가 아니었다. 실제로 그 13문항 안에 "아버지보다 수입이 적었는데도 돈을
> 벌었나요?" 같은 게 있었다.
>
> **"점수가 안 나오면 모델을 키운다"는 반사적 대응이 여기서는 틀렸다.**
> 원인을 가르지 않고 모델을 바꿨으면 "Gemini가 더 나쁘다"는 엉뚱한 결론에
> 도달했을 것이다.

## 4-1. 그래서 층화 표집(stratified sampling)을 넣었다

### 층화 표집이 뭔가

**성격이 다른 하위 집단(= 층, stratum)이 섞여 있을 때, 전체에서 무작위로 뽑지 않고
층별로 나눠서 뽑는 것.**

학교로 비유하면 이렇다. 전교생 1,000명 중 3학년이 30명이다. 무작위로 100명을 뽑아
설문하면 3학년은 3명쯤 들어온다. 그 3명으로 "3학년 의견"을 말할 수는 없다.
3학년 얘기가 궁금하면 **3학년 명단에서 따로 뽑아야** 한다.

**우리 코퍼스에서 벌어진 일이 정확히 이거다:**

| 층 | 청크 수 | 비율 | 무작위 100개에 몇 개? |
|---|---|---|---|
| PMC 논문 | 10,937 | 96.3% | 약 96개 |
| 보호자용 기관 문서 | **320** | **2.8%** | **약 3개** |

무작위 표본은 사실상 **논문 표본**이다. 판정기가 0/10을 준 건 판정기가 틀려서가
아니라 **논문만 보여줬기 때문**이다.

### 대가 — 층에서 뽑은 표본은 그 층만 대표한다

이게 층화 표집을 쓸 때 반드시 같이 기억해야 하는 것이다. `owner-docs` 층으로 만든
평가셋은 **"이 시스템이 ASPCA를 잘 찾는가"**를 재지, **"코퍼스 전체를 잘 찾는가"**를
재지 않는다.

그래서 각 문항에 **어느 층에서 왔는지(`stratum`)를 기록**한다. 나중에 지표를 층별로
쪼개 볼 수 있어야 쓸모 있는 문장이 나온다 — "전체 60%"보다 "가이드 문서는 80%,
논문은 20%"가 훨씬 많은 걸 말해준다.

### 이 프로젝트의 층 나누기

무작위로 뽑으면 코퍼스 구성이 그대로 반영된다. 우리 코퍼스는 논문이 96%라,
무작위 표본은 곧 **논문 표본**이다.

```bash
uv run python -m scripts.eval.generate_qa --stratum owner-docs --n 240
```

| 층 | 대상 | 청크 수 |
|---|---|---|
| `all` | 코퍼스 전체 | 11,354 |
| `owner-docs` | ASPCA·RSPCA·VCA·AVSAB | **320 (2.8%)** |
| `papers` | PMC 논문 | 10,937 |

> ⚠️ **AAHA는 `owner-docs`에서 뺐다.** `doc_type`은 `guide`지만 **수의사용 진료
> 지침**이라 보호자 문서와 성격이 다르다. 실측에서도 절반이 RESEARCH로 판정됐다
> (제목 페이지, 약어 목록, 후원 문구). **`doc_type`이라는 기존 분류를 그대로
> 믿지 않고 실제 판정 결과를 보고 층을 다시 그은 것이다.**

**이 층으로 만든 평가셋의 한계도 분명하다.** 전체의 2.8%만 대상으로 하므로,
"이 시스템이 ASPCA를 잘 찾는가"를 재지 "코퍼스 전체를 잘 찾는가"를 재지 않는다.
그래서 생성된 각 문항에 **어느 층에서 왔는지(`stratum`)를 기록**한다.

### 이 발견 자체가 제품에 대해 말해주는 것

보호자 질문에 답할 수 있는 청크가 **320개(2.8%)**뿐이라면, 나머지 11,000개는
검색 결과를 흐리는 역할만 하고 있을 수 있다. 이건 평가셋 문제가 아니라
**코퍼스 전략 문제**다 — 기관 가이드를 더 넣어야 한다는 뜻이고, 이 프로젝트가
"코퍼스를 25배 늘렸는데 체감이 그대로"였던 이유이기도 하다.

## 4-2. 로컬 모델로 평가셋 키우기 — 판정기부터 보정한다

Gemini 무료 티어의 **일일 할당량이 소진돼** 평가셋이 144문항에서 멈췄다. 로컬
`gemma-4-e2b`로 이어가려 했는데, 그러려면 먼저 알아야 할 게 있었다.

### 같은 프롬프트인데 모델이 바뀌면 판정기의 성격이 바뀐다

`owner-docs` 층에서 gemma를 돌려보니 **검증 단계가 12개 중 9개(75%)를 거절**했다.
같은 프롬프트로 Gemini는 225개 중 13개(5.8%)만 거절했는데. 게다가 거절된 것 중에
멀쩡한 질문이 많았다:

```
✗ 보호자가 떠날 준비를 할 때 강아지가 불안해하는 신호는 무엇인가요?   ← 좋은 질문인데 거절
✗ 병원 예약은 어떻게 하나요?                                        ← 이건 거절이 맞다
```

### 프롬프트를 고치기 전에, 판정기를 채점했다

**"더 많이 통과시키게" 조정하면 아무거나 통과하는 쪽으로 무너지는데, 통과율만
보면 그걸 알아챌 수 없다.** 그래서 정답을 아는 데이터를 만들었다:

| 데이터 | 만드는 법 | 정답 |
|---|---|---|
| 양성 | Gemini가 이미 YES로 통과시킨 (질문, 정답 청크) 쌍 | YES |
| 음성 | 같은 질문 + **다른 문서**의 청크 | NO |

> 음성을 만들 때 **같은 문서의 다른 청크는 쓰면 안 된다.** 그건 실제로 답이 될 수
> 있어서 정답이 NO라고 단정할 수 없다 (06장의 "문서 단위 채점"이 그래서 있다).

```bash
uv run python -m scripts.eval.calibrate_judge --n 40
```

**결과 (gemma-4-e2b, 양성 40 + 음성 40):**

| 프롬프트 변형 | 양성(좋은 쌍을 YES) | 음성(엉뚱한 쌍을 NO) | 균형 |
|---|---|---|---|
| 긴 설명 (원래) | 32% | 100% | 66% |
| **짧게** | **42%** | 100% | **71%** |
| 긍정형으로 질문 | 28% | 100% | 64% |

두 가지를 알았다:

- **NO 조건을 길게 나열한 게 작은 모델을 NO 쪽으로 밀고 있었다.** 덜어내니 10%p 올랐다
- **음성이 세 변형 모두 100%다.** gemma는 명백히 무관한 건 잘 거르고,
  **애매한 건 전부 NO로 민다**

### 그래서 검증을 껐다 — 근거는 짝지은 검정의 성질

42%도 여전히 좋은 질문의 58%를 버린다. 끄는 쪽과 비교하면:

| 방식 | 189청크에서 수확 | 판별력 있는 문항 |
|---|---|---|
| 검증 켬 | ~79 | ~79 |
| **검증 끔** | **186** | ~130 |

**넓거나 막연한 질문은 잡음이 아니라 무익하다.** 어떤 설정에서도 결과가 같으므로
짝지은 비교(04장)의 불일치 쌍에 기여하지 않는다 — **검정력을 깎지 않고 절대 점수만
낮춘다.** 반면 좋은 질문을 버리는 건 판별력 있는 문항을 직접 잃는 것이다.

> 이게 12장(LLM as a judge)에서 쓸 절차의 예고편이다. **LLM에게 판정을 시킬 때는
> 판정기 자체를 검증셋으로 재는 것**이 표준이다.

## 4-3. 검증을 끄고 나서 실제로 터진 문제는 예상과 달랐다

검증을 끄면 "막연한 질문이 섞인다"는 건 예상했고 비용도 계산했다. 그런데
**결과물을 직접 읽어보니 진짜 피해는 다른 데 있었다.**

```
4번.  우리 강아지가 불안해 보일 때는 어떻게 해야 하나요?   → 청크 A가 정답
13번. 우리 강아지 불안할 때 어떻게 해야 하나요?           → 청크 B가 정답
```

거의 같은 질문인데 정답이 다르다. 전체를 세어보니 **330문항 중 유사 질문 쌍이 58개,
전부 정답 청크가 달랐다.**

**이건 막연한 질문과 성질이 다르다. 무익한 게 아니라 유해하다.** 같은 질문에 정답이
둘이면 검색이 무엇을 1위로 올리든 하나는 반드시 오답으로 세어지고, 설정을 바꿀 때마다
엉뚱하게 뒤집히며 잡음을 만든다.

```bash
uv run python -m scripts.eval.generate_qa \
    --merge data/eval_auto_qa_owner.jsonl data/eval_auto_qa_owner2.jsonl \
    --out data/eval_auto_qa_merged.jsonl
```

유사도 0.85 임계로 37건을 제거해 **293문항**이 됐다 (Gemini 134 + gemma 159).
앞에 둔 파일이 이기므로 품질이 높은 쪽이 살아남는다.

> **예상한 부작용만 확인하고 넘어갔으면 58개의 충돌 라벨을 안고 08장 실험을 했을
> 것이다.** 자동 생성물은 통계만 보지 말고 실제로 읽어야 한다.

## 4-4. "막연한 질문"이라는 이름부터 틀렸다

위에서 표본 20개를 읽고 4개를 "명백히 공허함"으로 분류했다. **그 판단이 틀렸다.**

```
우리 강아지가 불안해 보일 때는 어떻게 해야 하나요?
집에서 어떻게 훈련을 시작해야 하나요?
```

**실사용에서는 오히려 이런 질문이 더 흔하다.** 보호자는 "분리불안 시 외출 전 인사
단축이 도움이 되나요?"라고 묻지 않는다. 불안해 보인다고 말한다.

문제는 질문이 아니라 **채점 방식**이다:

| | 넓은 질문 | 좁은 질문 |
|---|---|---|
| 실사용 현실성 | **높다** | 낮다 |
| 답이 되는 청크 수 | 수십 개 | 하나 |
| "정답은 이 청크" 라벨 | **성립 안 함** | 성립함 |
| 맞는 채점 단위 | **문서 단위** | 청크 단위 |

좁은 질문에만 맞는 가정을 넓은 질문에도 적용하니 부당하게 실패로 세어진 것이다.

**그래서 버리지 않고 라벨을 붙인다:**

```bash
uv run python -m scripts.eval.label_breadth --qa data/eval_auto_qa_merged.jsonl --sample 15
```

### 쪼개서 재봤더니 — 예상이 틀렸다

**예상:** 넓은 질문은 답이 여러 청크에 흩어져 있으니, **넓은 질문에서만**
청크→문서 격차가 크게 벌어질 것이다.

**실측 (293문항):**

| 그룹 | 문항 | 청크 hit@5 | 문서 hit@5 | 격차 |
|---|---|---|---|---|
| specific | 138 | 55.8% | 89.9% | **+34.1%p** |
| broad | 155 | 43.9% | 73.5% | +29.7%p |

**격차는 오히려 좁은 질문이 더 컸다.** 예상이 빗나갔다. 즉 청크→문서 격차는
질문의 넓이 탓이 아니라 **"정답은 청크 하나" 라벨 방식 자체의 성질**이고,
두 그룹에 똑같이 나타난다.

대신 데이터가 말한 건 다른 것이다:

> **넓은 질문은 문서 단위에서도 26.5% 실패한다.** 청크·문서 두 지표 모두 좁은
> 질문보다 12~16%p 낮다. **채점 방식 문제에 더해, 실제로 검색이 더 어려운
> 질문이다.** "훈련은 어떤 방식이 가장 좋을까요?"는 정답 문서라는 것 자체가 애매하다.

그래서 결론이 바뀐다:

- **채점 페널티(~30%p)는 두 그룹 공통** → 절대 점수는 **문서 단위를 같이 봐야 한다**
- **넓은 질문은 그 위에 추가로 어렵다** →
  **되묻기(`coverage=needs_detail`)가 정답인 영역**이다

이 프로젝트에는 그 경로가 **이미 있다.** 넓은 질문에 훈련사가 하는 일은 자료를
찾아주는 게 아니라 "혼자 있을 때만 그러나요?"라고 되묻는 것이다.
**IR 지표는 그 동작을 볼 수 없다** — 평가셋 하나로 모든 걸 재려 하면 안 된다.

### 부수 확인 — 두 모델의 문항을 섞어도 되나

| 생성 모델 | 문항 | 청크 hit@5 | 문서 hit@5 |
|---|---|---|---|
| Gemini | 134 | 51.5% | 82.8% |
| gemma-4-e2b | 159 | 47.8% | 79.9% |

**차이가 작다.** 섞어 쓴 게 지표를 크게 흔들지 않으므로 293문항을 한 세트로 쓴다.
`generator` 필드를 남겨둔 덕에 이걸 확인할 수 있었다.

질문 길이 분포, 문서별 쏠림, 중복 질문, 그리고 **샘플 5개의 질문+정답 청크**를
같이 보여준다. 라벨이 맞는지는 원문을 봐야 안다.

> 자동 생성은 **초안이지 완성이 아니다.** 이 장에서 세 번 무너진 게 전부
> "출력을 안 보고 믿어서" 생긴 일이다.

---

## 요점 3줄

1. **질문을 만든 청크가 곧 정답이다.** 이게 자동 생성의 전부고, 덕분에 사람이
   라벨링하지 않아도 hit rate·MRR을 잴 수 있다.
2. **작은 모델에는 한 호출에 한 가지만 시킨다.** 판정+생성을 묶으면 판정을 버린다.
   그래서 분류 → 생성 → 검증 세 단계로 쪼갰다.
3. **자동 평가셋은 절대 점수용이 아니라 비교용이다.** "정답이 하나"라는 가정 때문에
   점수가 실제보다 낮게 나오고, 질문 말투도 실사용과 다르다.
