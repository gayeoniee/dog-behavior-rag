# 08. 임베딩 모델 선정 — 리더보드로 고르지 않는다

← [06. 검색 품질 지표](06-ir-metrics.md) · [체크리스트로](00-checklist.md)

---

## 1. 지금 모델은 어떻게 골랐나

`.env` 주석이 솔직하다:

> 모델은 내일 데이터 보고 확정. bge-m3는 한국어 성능 좋은 무료 임베딩 모델

**"내일 확정"이 안 됐다.** 비교한 적이 없다. 멘토가 짚은 지점이 이것이다:

> "좋은 임베딩 모델 알려줘" 말고, **실제 리더보드 사이트들을 찾아서 최신 모델들을
> 다 포함해 어떤 특징에 맞는 걸로 리스트업해줘** 식으로 요청하세요.

---

## 2. 리더보드는 후보를 좁히는 데 쓰고, 선택은 내 데이터로 한다

### 리더보드 1위는 우리 후보가 아니다

MMTEB(다국어) 상위권을 찾아보면 KaLM-Embedding-Gemma3-12B(72.32),
Qwen3-Embedding-8B(70.6) 같은 **8~12B급**이 나온다. 그런데 이 PC는:

```
VRAM 6GB  −  LM Studio가 쓰는 1.7GB  =  실제 가용 4GB 남짓
```

**돌아가지 않는 모델의 점수는 우리에게 정보가 아니다.** 제약을 먼저 적고 후보를
거른다:

| 제약 | 값 | 왜 |
|---|---|---|
| 모델 크기 | ~0.6B 이하 | VRAM 6GB를 LLM과 나눠 쓴다 |
| 차원 | **1024면 교체 공짜** | `chunks.embedding vector(1024)`와 `EMBEDDING_DIM` |
| 언어 | 교차언어 필수 | 질문은 한국어, 코퍼스는 100% 영어 |
| 라이선스 | 로컬 실행 가능 | API 비용·할당량을 피한다 |

### 후보 4개

| 모델 | 파라미터 | 차원 | 최대 길이 | 입력 규약 |
|---|---|---|---|---|
| BAAI/bge-m3 (현재) | 568M | 1024 | 8192 | 없음 |
| nlpai-lab/KURE-v1 | 568M | 1024 | 8192 | 없음 |
| intfloat/multilingual-e5-large | 560M | 1024 | **512** | **`query:`/`passage:` 필수** |
| Qwen/Qwen3-Embedding-0.6B | 596M | ≤1024 (MRL) | 32K | 질의에 `Instruct:` 권장 |

**넷 다 1024차원이라 채택 비용이 재임베딩뿐이다.** 차원이 다르면
`scripts.db.init --drop` + 전체 재적재가 붙는다.

> **KURE-v1을 넣은 이유:** bge-m3를 **한국어 200만 쌍**으로 파인튜닝한 모델이다.
> 한국어 검색 벤치마크에서 bge-m3를 앞선다고 알려져 있다.
>
> **그런데 우리 과제는 한국어 질문 → 영어 문서다.** 한국어 단일언어 검색에 맞춘
> 학습이 교차언어 정렬에 도움이 될지 해가 될지는 **리더보드로 알 수 없다.**

## 3. 공정하게 재려면 입력 규약을 지켜야 한다

모델 카드를 읽다가 발견한 것:

- **e5는 `query: ` / `passage: ` 접두사가 필수**다. 빼면 성능이 떨어진다고 명시돼 있다
- **Qwen3는 질의에 지시문**을 붙이면 1~5% 오른다고 한다
- **e5는 512토큰 상한**이라 긴 청크가 잘릴 수 있다

접두사를 안 붙이고 e5를 재면 그건 e5를 재는 게 아니라 **잘못 쓴 e5**를 재는 것이다.
04장에서 "지표가 특정 조건을 원리상 불리하게 만들지 않는지 확인하라"를 배웠는데,
여기서는 **입력 규약이 그 자리**다.

```bash
uv run python -m scripts.eval.embedding_experiment --models bge-m3 --distractors 150
```

통제한 것: 같은 청크(청킹은 한 번만 한다), 같은 질의(재작성 캐시 재사용),
같은 채점(구간 겹침 50%), 같은 방해 문서.

> ⚠️ **모델마다 프로세스를 나눠 돌려야 한다.** 한 프로세스에서 모델을 갈아끼웠더니
> 두 번째 로딩에서 **세그멘테이션 폴트(exit 139)** 로 죽었다. VRAM 6GB에서 이전
> 모델이 확실히 안 내려간다. 파이썬에서 CUDA 캐시를 비우는 걸로는 부족했고,
> 프로세스를 분리하니 OS가 정리해줘서 해결됐다. 그래서 결과 파일을 **누적**하도록
> 만들었다(조건이 다르면 이전 결과를 버린다).

## 4. 결과

**293문항, 방해 문서 150건, 청크 6,696개**

| 후보 | 차원 | hit@1 | hit@5 | hit@10 | MRR |
|---|---|---|---|---|---|
| **bge-m3 (현재)** | 1024 | 23.9% | 48.5% | 59.7% | 0.346 |
| KURE-v1 | 1024 | 24.2% | 49.1% | **62.1%** | 0.355 |
| e5-large | 1024 | 13.3% | **38.6%** | 47.1% | 0.236 |
| Qwen3-0.6B | 1024 | **26.3%** | **51.2%** | 59.0% | **0.365** |

### 짝지은 검정 (bge-m3 대비, hit@5)

| 후보 | 한쪽만 성공 | p값 | 판정 |
|---|---|---|---|
| KURE-v1 | 8 : 10 | 0.815 | 구별 불가 |
| **e5-large** | **58 : 29** | **0.002** | **유의미하게 나쁨** |
| Qwen3-0.6B | 28 : 36 | 0.382 | 구별 불가 |

> **이 프로젝트에서 처음으로 유의미한 차이가 나왔다.** 04장 청킹 실험에서는 어떤
> 쌍도 구별되지 않았는데, 여기서는 e5가 확실히 갈렸다. **모델 간 차이가 청크 크기
> 차이보다 훨씬 크다**는 뜻이고, 평가셋을 293문항으로 키운 게 값을 했다.

### e5가 나쁜 건 512토큰 때문인가 — 아니다

e5만 최대 길이가 짧아서, **모델이 약한 건지 청크가 잘린 건지** 갈라야 했다.
e5 토크나이저로 실제 청크를 재봤다:

```
표본 1,386청크 · 중앙 245 · p95 303 · 최대 402토큰
512토큰 초과(잘림): 0개 = 0.0%
```

**잘린 청크가 하나도 없다.** 교란 요인이 제거됐으니 e5의 10%p 열세는
**모델 자체가 이 과제에서 약한 것**이다.

> 이걸 확인 안 하고 "e5는 512라서 불리했다"고 적었으면 **틀린 이유를 기록으로
> 남길 뻔했다.** 결론보다 이유가 오래 간다.

### 속도 — 어느 속도를 재느냐가 중요하다

처음엔 대량 임베딩 속도만 재고 "bge-m3가 1.4배 빠르니 유지"라고 결론지었다.
**그건 잘못 짚은 것이다.** 그 숫자는 재적재 때 한 번 드는 오프라인 비용이다.

| | bge-m3 | Qwen3 | 성격 |
|---|---|---|---|
| 대량 임베딩 (11,354청크) | 10분 | 15분 | **한 번 드는 오프라인 비용** |
| **요청당 질의 임베딩** | **22.8ms** | **53.8ms** | 사용자가 겪는 비용 |

전체 채팅 응답이 **약 14초**(LLM 생성이 대부분)다. 31ms 차이는 **0.2%라 체감되지
않는다.**

> **속도는 여기서 가름 기준이 못 된다.** "빠른 쪽"이라는 말을 쓰기 전에
> **어느 속도가 사용자에게 닿는지** 먼저 물어야 했다.

### "유의미하지 않다"는 "차이가 없다"가 아니다

Qwen3의 28:36을 신뢰구간으로 옮기면:

> **hit@5 +2.7%p, 95% 신뢰구간 [−2.6%p, +8.1%p]**

**점추정은 Qwen3 쪽이고 최대 +8%p까지 열려 있다.** p=0.382는 "이 표본으로는
확정 못 한다"는 뜻이지 "같다"는 뜻이 아니다. MRR도 0.365 vs 0.346으로 Qwen3가
앞선다(MRR은 상위권 변화에 민감해 hit rate보다 예민한 지표다).

### MRL — 벡터를 잘라 쓰기

Qwen3는 **MRL(Matryoshka Representation Learning)** 로 학습됐다. 러시아 인형처럼
**앞부분만 잘라도 그 자체로 쓸 만한 벡터**가 되도록 훈련한 것이다. 보통 임베딩은
1024개를 통째로 써야 하고 앞 256개만 쓰면 뜻이 망가진다.

차원이 줄면 **저장·메모리·검색 비용이 함께 준다.** 임베딩은 한 번만 하고 자르기만
하면 되므로 실험이 거의 공짜다(단, **자른 뒤 재정규화해야 한다** — 안 하면 길이가
1이 아니라서 내적이 코사인 유사도가 아니게 된다).

| 차원 | hit@5 | MRR | bge-m3 대비 | 벡터 저장 |
|---|---|---|---|---|
| 1024 | 51.2% | 0.365 | p=0.382 구별 불가 | 46MB |
| **512** | **50.5%** | **0.366** | p=0.545 구별 불가 | **23MB** |
| 256 | 45.7% | 0.323 | p=0.396 구별 불가 | 12MB |
| 128 | 39.2% | 0.278 | **p=0.002 나쁨** | 6MB |
| 64 | 33.4% | 0.242 | **p=0.000 나쁨** | 3MB |

**512차원이 1024와 사실상 같다.** MRR은 오히려 미세하게 높다. **절반을 공짜로
얻는 셈**이고, 128 아래로 내려가면 확실히 무너진다.

## 5. 결론 — 확실한 것 하나, 애매한 것 하나

| 후보 | 판정 | 이유 |
|---|---|---|
| **e5-large** | ❌ **배제** | **유의미하게 나쁘다** (p=0.002). 이건 확실하다 |
| KURE-v1 | ❌ | 정확도 동률에 이점이 없다 |
| **bge-m3 (현재)** | ✅ 유지 가능 | 지금 잘 돌고 있고 바꿀 확실한 근거가 없다 |
| **Qwen3@512** | ⚖️ **바꿀 만하다** | 점추정 +2.0%p · MRR 우위 · **저장 절반** |

**bge-m3 vs Qwen3@512는 판단이 갈리는 자리다. 숫자를 정직하게 놓으면:**

| | bge-m3 | Qwen3@512 |
|---|---|---|
| hit@5 | 48.5% | 50.5% (구별 불가) |
| MRR | 0.346 | **0.366** |
| 벡터 저장 | 46MB | **23MB** |
| 질의 지연 | 22.8ms | 53.8ms (**전체의 0.2%**) |
| 바꾸는 비용 | — | `EMBEDDING_DIM=512` + 재적재 15분 |

**지금 규모에서는 어느 쪽도 정답이 아니다.** 46MB냐 23MB냐는 이 코퍼스에서
무의미하고, 정확도 차이는 확정되지 않았다. 그래서 **바꾸지 않는 것도, 바꾸는 것도
합리적이다.**

**다만 코퍼스가 커지면 계산이 달라진다.** 100만 청크가 되면 4GB vs 2GB이고,
그때는 정확도 동률에 저장 절반인 쪽이 확실히 낫다.

**04장과 같은 결말이지만 얻은 것이 다르다.** 청킹 실험은 "아무것도 구별 못 함"으로
끝났지만, 여기서는 **하나를 확실히 배제**했다. e5로 갈아탔다면 hit@5가 10%p
떨어졌을 텐데, 리더보드만 봤다면 충분히 고를 만한 모델이었다.

### 세 가지가 확인됐다

1. **한국어 특화 파인튜닝이 우리 과제에는 도움이 안 된다.** KURE는 한국어 검색
   벤치마크에서 bge-m3를 앞서는데 여기서는 동률이다. **우리 과제는 한국어 검색이
   아니라 한국어→영어 교차언어 검색**이라 학습이 겨냥한 곳이 다르다
2. **`.env`의 "내일 확정" 주석을 이제 지울 수 있다.** bge-m3는 이제 근거 있는 선택이다
3. **Qwen3@512가 실질적인 대안이다.** MRL 덕에 512차원에서 성능을 유지하므로
   저장이 절반이다. 코퍼스가 커지는 순간 이쪽이 낫다

## 6. 실제로 갈아타 봤다 — 그리고 되돌렸다

위 결론("바꿀 만하다")을 믿고 **진짜로 Qwen3@512로 교체했다.** `.env`를 바꾸고
`init --drop` + 재적재(GPU 15분)까지 했다. **그리고 되돌렸다.**

### 부분 코퍼스의 우위가 전체에서 사라졌다

| 조건 | 코퍼스 | 차원 | 청크 hit@5 |
|---|---|---|---|
| bge-m3 (기준) | 전체 11,354청크 | 1024 | **49.5%** |
| **실험 (4절)** | **부분 6,696청크** | 1024 | **51.2%** |
| Qwen3 실전 | 전체 11,354청크 | 512 | 49.1% |
| Qwen3 실전 | 전체 11,354청크 | **1024** | **49.5%** |

**1024로 돌려도 49.5%로 소수점까지 같다** (짝지은 검정 35:35, **p=1.000**).
512로 자른 탓이 아니었다.

> **실험에서 방해 문서를 150건으로 줄인 게 결론을 만들었다.** GPU 비용을 아끼려고
> 부분 코퍼스를 쓴 건데, 방해 요소가 1.7배가 되자 **+2.7%p 우위가 정확히 0이 됐다.**
>
> **실험 규모를 줄이면 비용은 아끼지만 결론이 바뀔 수 있다.** 부분 코퍼스에서 이긴
> 모델은 "이겼다"가 아니라 "그 규모에서는 이겼다"로 읽어야 한다.

문서 단위에서는 오히려 밀렸다 — MRR 0.689 → 0.653, 그리고 21문항 검사의
**실무 문서 평균이 3.9 → 3.0**으로 떨어졌다. 정답 청크는 비슷하게 찾는데
**같은 문서의 다른 청크를 상위로 못 끌어올린다.** 답변에는 top 5가 통째로
들어가므로 이건 체감에 닿는다.

### 갈아타는 과정에서 세 개의 함정을 밟았다

**전부 에러가 안 나고 조용히 틀리는 종류였다.**

**① `chunk_id`는 재적재하면 새로 매겨진다**

평가셋은 정답을 `chunk_id`(DB serial)로 저장한다. `init --drop` 후 재적재하니
id가 전부 바뀌어 **라벨이 엉뚱한 청크를 가리켰다.** 그 상태로 지표를 재니:

```
청크 hit@5  49.5% → 0.7%
```

**하마터면 "Qwen3가 검색을 망가뜨렸다"고 결론 내고 끝낼 뻔했다.** 그걸 막은 건
**두 지표가 서로 안 맞았다는 점**이다 — 같은 DB로 돌린 21문항 검사는 18/21로
멀쩡했다. 검색이 정말 죽었다면 21문항도 같이 죽었어야 한다. 그 모순이
"모델이 아니라 측정을 의심하라"는 신호였다.

> 고약한 건 **항상 깨지지는 않는다**는 점이다. 두 번째 재적재에서는 id가 그대로였다
> — 원래 DB가 여러 세션에 걸쳐 점진적으로 적재돼 순서가 달랐던 것뿐이다.
> **어떤 때는 멀쩡하고 어떤 때는 조용히 틀린다.**

해법: `--remap`으로 청크 본문을 대조해 다시 맞추고, 재발 방지로 **`doc_hash` +
`ordinal`**(재적재와 무관하게 안정적)을 함께 저장한다.

```bash
uv run python -m scripts.eval.generate_qa --remap data/eval_auto_qa_merged.jsonl
```

**② 테스트가 개발자의 `.env`를 읽고 있었다**

`EMBEDDING_DIM`을 512로 내리자 **테스트 25개가 한꺼번에 깨졌다.** 코드는 멀쩡한데
`.env`가 바뀌었기 때문이다. 그전까지 통과한 건 격리돼서가 아니라 **`.env` 값이
우연히 기본값과 같아서**였다.

새 기여자의 `.env`, CI의 빈 `.env`, 실험 중인 내 `.env`가 전부 다른 결과를 내면
테스트는 신호가 아니라 잡음이 된다. `tests/conftest.py`에서 `.env` 로딩을 끊었다.

**③ `.env`의 `
`은 줄바꿈이 아니다**

Qwen3의 접두사는 `"Instruct: ...
Query: "`처럼 **줄바꿈이 의미를 갖는다.**
그런데 `.env`는 값을 문자 그대로 읽어서 역슬래시와 n 두 글자가 들어왔다.
**에러 없이 접두사만 이상해진 채 임베딩이 된다.** 설정 계층에서 풀도록 고쳤고,
후행 공백까지 실험 조건과 맞췄다 — 안 맞추면 4절에서 잰 숫자가 무효가 된다.

### 그래서 무엇이 남았나

**결론은 4절과 같지만("bge-m3 유지") 근거가 바뀌었다.** 4절에서 든 근거(속도)는
틀렸고, 진짜 이유는 **전체 규모에서 우위가 재현되지 않는다**는 것이다.

그리고 **되돌리는 비용이 낮게 설계돼 있어서 이 실험이 가능했다.** DB는 파생물이고
원본은 `corpus.jsonl`이라, 되돌리기가 `.env` 세 줄 + 재적재 15분이었다.
**되돌리기 쉬우면 과감하게 시도할 수 있다.**

- **코퍼스가 한국어를 포함하게 되면** — KURE의 판정이 뒤집힐 수 있다
- **재랭킹까지 포함해서** — 지금은 순수 코사인만 비교했다
- **처음부터 전체 코퍼스로** — 부분 코퍼스가 만든 착시를 이번에 확인했다.
  GPU 시간을 아끼려면 후보를 먼저 좁히고, **최종 후보만 전체로 재는 2단계**가 낫다
