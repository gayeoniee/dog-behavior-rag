# 12. LLM as a judge — 답변 자체를 재다

## 1. 지금까지 무엇을 안 재고 있었나

01~09장에서 청킹·임베딩·검색·하이브리드를 전부 숫자로 쟀다. 그런데 **답변 자체는
한 번도 안 쟀다.** 사람이 읽어보는 것뿐이었다.

06장이 이미 그쪽을 가리키고 있었다:

> **문서 단위 hit@1이 59.0%다.** 질문의 6할은 정답 문서를 바로 1위로 올린다.
> 체감 품질이 그보다 낮다면 그건 검색이 아니라 **근거 선별이나 답변 생성** 쪽
> 문제일 수 있다.

## 2. 무엇을 재는가 — 충실성이 핵심이다

RAG의 존재 이유는 **"자료에 없으면 말하지 않는다"**이다. 그러니 답변이 근거에
없는 내용을 말하면 검색을 아무리 잘해도 의미가 없다.

| 지표 | 무엇을 잡나 |
|---|---|
| **근거 충실성 (faithfulness)** | **환각** — 답변이 근거를 벗어났는가 |
| 질문 응답성 (relevance) | 동문서답 |

**한 호출에 하나씩 묻는다.** 05장에서 "작은 모델은 두 가지를 묶으면 하나를
버린다"를 비싸게 배웠다.

```bash
uv run uvicorn app.main:app          # 답변을 받아와야 하므로 API가 떠 있어야 한다
uv run python -m scripts.eval.answer_judge --n 8 --calibrate
```

## 3. 첫 시도가 포화했다 — 지표 설계의 함정

처음에는 이렇게 물었다:

> "답변의 **모든** 주장이 근거에 있는가? YES/NO"

**결과가 전부 NO였다** (Gemini 0/6, gemma 1/6). 당연하다 — 문장 하나만 어긋나도
NO다. 그런데 **그러면 개선을 잴 수 없다.** 고치기 전과 후가 똑같이 0이면 그 지표는
아무것도 말해주지 않는다.

> **이진 판정이 한쪽으로 포화하면 비율로 바꾼다.**
>
> 문장 단위로 물어 "지지된 문장 / 전체 문장"을 내면, 6문장 중 2문장이 어긋난
> 답변과 5문장이 어긋난 답변이 구별된다.

호출 수가 답변 문장 수만큼 늘지만(답변당 5~7회) 답변 평가는 오프라인이라 감수한다.
04장의 "천장을 먼저 계산하라", 09장의 "포화 여부를 확인하라"와 같은 계열의 교훈이다.

## 4. 판정기를 믿기 전에 판정기를 잰다

05장에서 만든 절차를 그대로 쓴다. **정답을 아는 쌍**이 필요한데, 답변 평가에서는
이렇게 만든다:

| | 만드는 법 | 정답 |
|---|---|---|
| 양성 | 실제 답변 + **그 답변이 실제로 쓴 근거** | 충실해야 함 |
| 음성 | 실제 답변 + **다른 질문의 근거** | 불충실이어야 함 |

**근거 바꿔치기가 핵심이다.** 답변은 그대로 두고 근거만 바꾸면 **답변 내용은
멀쩡한데 근거와의 관계만 끊긴다.** 판정기가 이걸 통과시키면 근거를 안 보고
"말이 되는가"만 보고 있다는 뜻이고, 그런 판정기는 환각을 못 잡는다.

### 실측 (Gemini 판정, 8문항)

```
양성(진짜 근거)에서 지지된 문장 비율   34%
음성(바꿔친 근거)을 불충실로 적발      100%
균형 정확도                            67%   (찍기 = 50%)
```

> ⚠️ **음성 적발률만 보면 속는다.** "항상 NO"라고 답하는 판정기도 음성은 100%다.
> 양성까지 같이 봐야 **판정하는 것과 한쪽으로 미는 것**이 갈린다.
>
> 이 판정기는 음성은 잘 잡지만 양성을 자주 버린다 → **실제 충실성은 측정값보다
> 높을 것이다.** 결과를 그만큼 할인해서 읽어야 한다.

## 5. 결과 — 답변 문장의 70%가 근거 밖이다

**8문항 · 채점한 주장 43개 · 판정 Gemini**

| 지표 | 값 |
|---|---|
| **근거 충실성 (문장 단위)** | **13/43 (30%)** |
| 전부 지지된 답변 | **0/8** |
| 질문 응답성 | 7/8 (88%) |

| coverage | 충실성 |
|---|---|
| full | 2/5 (40%) |
| partial | 11/33 (33%) |

### 무엇이 걸렸나

```
✗ 1. 잠자리에 들기 전에 짧게 산책을 시켜서 에너지를 소모하게 하세요
✗ 2. 외출 직전에 칭찬과 간식을 주어 긍정적인 경험을 만드세요
```

**틀린 조언이 아니다.** 일반적으로 맞는 말이다. 문제는 **근거 문서에 없다**는 것이다.
그러면 이 시스템은 "자료에 기반한 답변"이 아니라
**LLM의 일반 지식에 인용을 덧붙인 것**이 된다.

> CLAUDE.md에 적힌 사용자 표현이 아직 유효하다는 뜻이다 —
> **"그냥 제미나이랑 대화하는 느낌"**.
>
> 근거 선별(`evidence_select`)을 넣어 "코퍼스에 없으면 거절"은 해결했는데,
> **"근거는 있지만 답변이 그걸 안 쓰는"** 경우는 아직 아무도 안 보고 있었다.

### 06장의 예상이 맞았다

문서 단위 hit@1이 59%로 검색은 꽤 하는데 체감이 낮다면 병목은 검색이 아니라
답변 생성이라고 했다. **실제로 그렇다.**

## 6. 원인을 잘못 짚었다가 프롬프트를 읽고 찾았다

**첫 가설은 "폼이 빈칸을 만든다"였다.** 진단 + 단계 3개 + 주의점 + 병원을 강제하니
근거에 2개뿐이어도 3개를 채운다는 것이다. 그럴듯했다.

**프롬프트를 실제로 읽어보니 틀렸다.** 폼은 이미 조건부로 쓰여 있었다:

```
단계는 최대 3개              ← 정확히 3개가 아니다
주의점:은 쓸 말이 있을 때만
통증이 의심될 때만 병원: 줄
```

게다가 근거를 지키라는 지시도 이미 있었다 — "자료에 없는 구체적 수치나 절차를
지어내지 마세요", "모르는 부분을 추측으로 메우지 마세요".

### 진짜 원인 — 프롬프트가 스스로와 싸우고 있었다

| 근거를 지키라는 쪽 | 근거를 벗어나게 미는 쪽 |
|---|---|
| "자료에 없는 수치·절차를 지어내지 마세요" | "자료는 **당신이 이미 아는 지식처럼** 녹여 쓰세요" |
| "추측으로 메우지 마세요" | "'자료에 언급이 없다'가 아니라 **대신 뭘 해야 하는지 알려줘야** 합니다" |
| | **"'체계적 둔감화를 실시하세요'(나쁜 예) → '소리를 작게 틀고 반응 없으면 간식'(좋은 예)"** |

**마지막이 결정적이다.** 전문 용어를 구체적 행동으로 바꾸라는 요구 자체가
**근거에 없는 수치·타이밍을 만들어내라는 뜻**이다. 근거에는
"systematic desensitization"만 있는데 프롬프트는 초·거리·순서를 요구한다.

그리고 **구체화 쪽이 더 세게 작동한다** — 좋은 예/나쁜 예가 딸려 있기 때문이다.
추상적 금지("지어내지 마세요")는 구체적 예시를 이긴 적이 없다.

## 7. 고치고 다시 쟀다 — 개선은 있지만 작다

세 곳을 고쳤다:

| 고친 것 | 어떻게 |
|---|---|
| 구체화에 조건을 붙였다 | "바꿔 쓸 내용은 **자료에서 가져온다**". 나쁜 예 추가: `"3초간 틀고 5분 뒤 반복"(자료에 없는 숫자)` |
| "자기 지식처럼"을 말투로 한정 | "출처를 문장에 드러내지 않을 뿐, **내용은 자료 안에** 있어야 한다" |
| 얇은 자료엔 짧게 | "단계 2개짜리가 **지어낸 3개짜리보다 낫다**" |

**같은 8문항 · 같은 판정기(gemma) · 프롬프트만 변경:**

| | before | after |
|---|---|---|
| 근거 충실성 | 10/44 (23%) | 18/41 (44%) |

**그런데 이 44%는 재현되지 않았다.** 같은 프롬프트로 다시 돌리니 15/40 (38%)였다.
답변 생성이 비결정적이라 실행마다 흔들린다.

> **한 번 재고 "44% 달성"이라고 적을 뻔했다.** 이 프로젝트가 04장에서 배운
> "±1은 잡음이다"가 답변 생성에도 그대로 적용된다 — **검색보다 더 심하다.**
> LLM이 매번 다른 문장을 쓰므로 채점 대상 자체가 달라진다.

**정직한 수치는 이렇다:**

| 범위 | 충실성 |
|---|---|
| 앞 8문항 before | 10/44 (23%) |
| 앞 8문항 after (재현) | **15/40 (38%)** ← 진짜 개선폭 |
| **전체 21문항 after** | **22/93 (24%)** |

## 7-1. 앞 8문항만 좋았다 — 나머지는 13%

전체를 재보고서야 보였다:

| 그룹 | 충실성 |
|---|---|
| 앞 8문항 | 15/40 (**38%**) |
| **나머지 13문항** | 7/53 (**13%**) |

앞 8문항은 **코퍼스가 잘 덮는 주제**(초인종 짖음·분리불안·입질)이고, 뒤쪽은
줄당김·리콜·꼬리 신호처럼 **자료가 얇은 주제**다.

```
[partial] 0%  산책할 때 줄을 너무 당겨서 팔이 아파요
[partial] 0%  이름 불러도 안 와요 오라고 하면 도망가요
```

**모델이 게을러서가 아니다. 근거가 없어서 지어낼 수밖에 없는 것이다.**

> **프롬프트로 짜낼 수 있는 건 여기까지다.** 05장의 "보호자용 청크 320개(2.8%)",
> 09장의 "둘 다 못 찾는 37%"가 여기서 답변 품질로 나타난다. 같은 병목의 세 번째 얼굴이다.

### 악화한 문항도 봐야 한다

```
1/6 → 0/5   손을 자꾸 깨물어요
    새 진단: "아기라서 그렇다기보다는 놀이와 행동의 차이를 구별해야 합니다"
```

**근거를 덜 지어내려다 모호해졌다.** 구체화를 억제하면 이런 부작용이 생긴다 —
"근거에 충실하되 쓸모 있게"는 여전히 열려 있는 긴장이다.

### 왜 이게 중요한가

**가설을 고치지 않았으면 아무것도 안 바뀌었을 것이다.** 폼을 유연하게 만드는 건
이미 되어 있었으니 손대봐야 소용없었다. **"그럴듯한 원인"과 "실제 원인"을 가르는
유일한 방법은 대상을 직접 읽는 것**이었다.

## 8. 다음에 할 일

44%도 낮다. 답변 문장의 절반 이상이 여전히 근거 밖이다.

| 후보 | 가설 |
|---|---|
| **근거 없는 문장 표시** | 일반 지식으로 덧붙인 부분을 답변에서 구분해 보여준다 |
| 코퍼스 보강 | 근거가 얇아서 못 채우는 것이라면 자료를 늘리는 게 근본이다 |
| 근거를 더 넣기 | top_k를 늘리면 채울 게 많아진다 (프롬프트 예산과 상충) |

**두 번째가 09장의 결론과 만난다** — "둘 다 못 찾는 37%"와 "보호자용 청크 2.8%".
프롬프트로 짜낼 수 있는 건 여기까지고, 그다음은 자료 문제다.

### 그리고 이 지표 자체도 아직 부족하다

- **8문항뿐이다.** Gemini 일일 할당량이 소진돼 21문항을 다 못 돌렸다
- **판정기가 양성을 자주 버린다** (34%). 프롬프트 보정이 더 필요하다
- **"근거에 없다"와 "틀렸다"는 다르다.** 지금 지표는 전자만 본다.
  일반 지식이 맞는 말이면 사용자에게는 유용할 수도 있다 — 다만 **인용을 붙이면 안 된다**

## 요점 3줄

1. **이진 판정이 포화하면 비율로 바꾼다.** "모든 주장이 지지되는가"는 전부 NO가
   나와서 개선을 잴 수 없었다. 문장 단위 비율로 바꾸니 30%라는 쓸 수 있는 숫자가 됐다.
2. **판정기를 믿기 전에 근거를 바꿔치기해서 시험하라.** 음성 적발률만 보면
   "항상 NO"인 판정기를 좋은 판정기로 오인한다.
3. **프롬프트를 고쳐 앞 8문항은 23% → 38%가 됐지만 전체 21문항은 24%다.**
   자료가 얇은 주제(줄당김·리콜)는 13%였다 — **근거가 없으면 충실할 수 없다.**
   프롬프트로 짜낼 수 있는 건 여기까지고, 그다음은 코퍼스 문제다.

## 이해 확인 질문

1. "답변의 모든 주장이 근거에 있는가?"를 YES/NO로 물었더니 전부 NO였다. 왜 문제인가?
2. 판정기가 음성(바꿔친 근거)을 100% 적발했다. 좋은 판정기인가?
3. 충실성이 30%인데 "답변이 틀렸다"고 결론 내도 되나?
