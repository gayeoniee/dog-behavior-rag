# 06. 검색 품질 지표 — hit rate와 MRR

**이 장으로 자가 완성된다.** 여기까지 오면 "청킹을 바꿨더니 좋아졌다"를 숫자로
말할 수 있다.

## 1. 지금까지 무엇을 못 재고 있었나

이 프로젝트에는 이미 평가셋이 있다 (`scripts.eval.retrieval_report`, 21문항).
그런데 그건 **통과/실패**만 본다.

```
✓ covered   0.712  ...  강아지가 초인종 소리에 계속 짖어요
```

여기서 알 수 없는 것:

- 정답이 **1등**이었나 **5등**이었나? (통과는 똑같이 통과다)
- 상위 3개만 쓰면 여전히 통과였을까?
- 청크를 800자로 바꾸면 순위가 올라갈까 내려갈까?

**검색은 "맞았나"가 아니라 "몇 등이었나"의 문제다.** 그래서 정보검색 분야에는
표준 지표가 따로 있다.

### 직접 확인

```bash
uv run python -m scripts.eval.ir_metrics --save baseline
uv run python -m scripts.eval.ir_metrics --compare baseline    # 무언가 바꾼 뒤
uv run python -m scripts.eval.ir_metrics --no-rewrite           # 질의 재작성 효과
```

## 2. hit rate — "상위 k개 안에 정답이 있었나"

가장 단순한 지표다.

```
hit rate@5 = (상위 5개 안에 정답이 있던 질문 수) / (전체 질문 수)
```

질문 10개 중 6개에서 정답이 top 5에 있었다면 hit rate@5 = 60%.

**여러 k에서 보는 이유:**

| k | 무엇을 말하나 |
|---|---|
| @1 | 1등을 맞혔나. 가장 가혹하다 |
| **@5** | **이 시스템의 진짜 기준** — `settings.top_k = 5`라 실제 답변에 5개만 쓴다 |
| @10 | 검색이 아예 못 찾은 건 아닌지. 리랭킹(10장)의 여지를 보여준다 |

@10은 높은데 @1이 낮다면 → **검색은 찾았는데 순서가 나쁘다** → 리랭킹으로 개선된다.
@10부터 낮다면 → **아예 못 찾는다** → 임베딩 모델이나 청킹을 봐야 한다.

## 3. MRR — "몇 등이었나"까지 본다

hit rate@5의 문제: **1등과 5등을 똑같이 센다.** 그런데 1등이 훨씬 낫다 —
프롬프트 앞쪽에 오고, top_k를 줄여도 살아남는다.

**MRR(Mean Reciprocal Rank)** 은 순위의 역수를 평균낸다.

| 정답 순위 | 점수 |
|---|---|
| 1등 | 1.000 |
| 2등 | 0.500 |
| 3등 | 0.333 |
| 5등 | 0.200 |
| 못 찾음 | 0 |

질문 3개에서 정답이 각각 1등·3등·못찾음이면
MRR = (1.0 + 0.333 + 0) / 3 = **0.444**.

> **MRR은 "평균 몇 등"이 아니다.** 역수의 평균이라 **상위권 변화에 훨씬 민감하다.**
> 2등을 1등으로 올리면 +0.5지만, 9등을 8등으로 올리면 +0.014다. 실제 사용자
> 체감과 같은 방향이다 — 아무도 9등을 안 본다.

## 4. 두 가지로 채점한다 — 05장의 한계에 대한 대응

자동 생성 평가셋은 **"정답은 그 청크 하나"**라고 가정한다. 그런데 우리 코퍼스에는
같은 문서에서 나온 비슷한 청크가 수십 개다. 그래서 두 가지로 잰다:

| 채점 | 무엇을 정답으로 보나 | 성격 |
|---|---|---|
| **청크 단위** | 질문을 만든 **바로 그 청크** | 엄격. 실제보다 **낮게** 나온다 |
| **문서 단위** | 그 청크가 속한 **문서의 아무 청크** | 관대. 실제보다 **높게** 나올 수 있다 |

**진짜 성능은 이 둘 사이 어딘가에 있다.**

실제로 이런 사례가 나왔다:

```
[ 6/13] 문서만   입양 후 강아지들의 행동은 어떻게 예측되나요?
                 → 정답 문서가 1위인데, 그 문서의 다른 청크가 올라왔다
```

**엄격 지표는 이걸 실패로 센다. 하지만 실사용에서는 성공이다** — 같은 문서의
인접 청크면 대개 같은 내용을 담고 있다.

## 5. 실측 — 지금 이 시스템의 baseline

```bash
uv run python -m scripts.eval.ir_metrics --save baseline
```

**13문항 · top_k=10 · 질의 재작성 켬** (2026-08-14)

| 지표 | 청크 단위(엄격) | 문서 단위(관대) |
|---|---|---|
| hit rate@1 | 23.1% | 46.2% |
| hit rate@3 | 38.5% | 61.5% |
| **hit rate@5** | **38.5%** | **61.5%** |
| hit rate@10 | 46.2% | 76.9% |
| **MRR** | **0.303** | **0.544** |

### 이 표에서 읽을 것

**(1) 13문항은 너무 적다. 1문항이 7.7%다.**
이 숫자로 "우리 검색은 38.5%"라고 말하면 안 된다. **지표를 만드는 것과 지표를
믿을 만큼 모으는 것은 다른 일이다.** 평가셋을 키우는 게 다음 할 일이다.

**(2) 엄격/관대 차이가 크다 (38.5% vs 61.5%).**
같은 문서의 다른 청크가 자주 올라온다는 뜻이다. 05장에서 예상한 그대로다.

**(3) @5와 @3이 같다 (38.5%).**
4~5등에서 새로 찾아지는 게 없다. 반면 @10은 46.2%로 오른다 →
**6~10등에 정답이 있는 질문이 하나 있다.** 리랭킹(10장)이 건드릴 수 있는 부분이다.

**(4) MRR 0.303은 "평균 3등쯤"이 아니다.**
못 찾은 7건이 0점으로 들어가서 낮다. 찾은 것만 보면 1등이 많다
(1위 3건, 2위 1건).

## 6. 이 지표로 무엇을 실험할 수 있나

여기서부터가 진짜 RAG 고도화다. **전부 같은 리듬이다:**

```
① --save baseline 으로 지금 점수를 저장
② 무언가 하나만 바꾼다
③ 재적재(필요하면) 후 --compare baseline
④ 어느 질문의 순위가 움직였는지 본다
```

| 장 | 바꾸는 것 | 재적재 필요? |
|---|---|---|
| 04 | 청크 크기·구분자 순서 | **필요** (GPU 15분) |
| 08 | 임베딩 모델 | **필요** (모델당 15분) |
| 09 | 하이브리드 검색 (BM25 추가) | 불필요 |
| 10 | 리랭킹 | 불필요 |
| 11 | parent-child 청킹 | **필요** |

`--compare`는 총점만이 아니라 **어느 질문이 움직였는지**를 보여준다.
총점이 같아도 안에서 뒤바뀌었을 수 있고, 그건 다른 얘기다.

## 7. 두 평가셋의 역할 분담

**둘 다 쓴다.** 재는 것이 다르다.

| | `retrieval_report` (21문항) | `ir_metrics` (자동 생성) |
|---|---|---|
| 질문 | 사람이 쓴 실사용 말투 | 기계 생성 |
| 채점 | 키워드 + LLM 근거 선별 | 정답 청크의 순위 |
| 재는 구간 | 검색 **+ 근거 선별** | **검색만** |
| 실행마다 흔들리나 | **흔들린다** (LLM 판정) | 흔들리지 않는다* |
| 잘 보는 것 | 거절 동작, 체감 품질 | 순위, 검색 자체의 성능 |

\* 질의 재작성이 LLM이라 그만큼은 흔들린다. **`--no-rewrite`로 끄면 완전히
결정적이 된다** — 순수하게 임베딩·청킹만 비교하고 싶을 때 쓴다.

> **이게 중요한 이유:** 검색을 바꾸는 실험을 `retrieval_report`로 재면
> LLM 판정의 잡음에 묻힌다. 반대로 거절 동작을 `ir_metrics`로는 아예 못 본다.

---

## 요점 3줄

1. **검색은 "맞았나"가 아니라 "몇 등이냐"의 문제다.** hit rate는 상위 k 안에
   있었는지를, MRR은 몇 등이었는지까지 본다.
2. **@1이 낮고 @10이 높으면 순서 문제(리랭킹), @10부터 낮으면 검색 자체의 문제**
   (임베딩·청킹)다. 어디를 고쳐야 할지가 표에서 읽힌다.
3. **13문항짜리 baseline은 방향만 본다.** 지표를 만든 것과 믿을 만큼 모은 것은
   다르다. 절대값이 아니라 `--compare`의 변화로 읽어야 한다.

## 이해 확인 질문

1. hit rate@5가 60%로 같은 A와 B가 있다. 어느 쪽이 나은지 어떻게 가리나?
2. hit rate@1 = 20%, @10 = 80%다. 무엇을 고쳐야 하나?
3. 청킹을 바꾸는 실험을 할 때 `retrieval_report`(21문항)가 아니라 `ir_metrics`를
   쓰는 게 나은 이유는?

<details>
<summary>답 보기</summary>

1. **MRR을 본다.** hit rate@5는 1등과 5등을 똑같이 세지만, MRR은 상위권일수록
   높은 점수를 준다. 둘 다 60%여도 MRR이 높은 쪽이 정답을 더 위로 올린 것이다.
2. **검색은 찾고 있는데 순서가 나쁘다** → 리랭킹(10장)이나 재랭킹 가중치를 본다.
   임베딩 모델을 바꾸는 건 우선순위가 낮다 — 이미 10등 안에는 들어와 있으니까.
3. `retrieval_report`는 **LLM 근거 선별까지 포함**해서 재므로 실행마다 점수가
   흔들린다(같은 코드로 두 번 돌려도 ±1). 청킹 변화 같은 작은 차이는 그 잡음에
   묻힌다. `ir_metrics --no-rewrite`는 LLM을 아예 안 써서 **완전히 결정적**이다.

</details>
